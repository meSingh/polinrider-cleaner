How to use this template. Delete this block before publishing.

Copy this file to docs-site/src/content/news/YYYY-MM-DD-short-slug.mdx.
`date` is the day it is published, in Asia/Kolkata, and is never changed
afterwards. `review` is the date of the indicator review the post comes from;

When to write one: only when a week changes what a reader would do. A new
way in, a new file or artifact on disk or in a repository, a new way it
survives cleaning or a cluster large enough that many readers may have
installed it. A week that only adds package names is not a post. Every week
stays recorded in the indicator reviews either way.

Who it is for: a developer who has just heard of this, or just found it on
their own machine. Write like someone who has cleaned it up on their own
computers and is explaining it to a colleague. Not like a report, and not for
a search engine.

How it reads:

1. 500 to 900 words. Three to five minutes.
2. The headline says what is new. The first paragraph says what happened and
   who it affects, in plain words.
3. Prose, with three to five short subheadings. No bullet walls with bold
   labels, no "key facts" lists, no FAQ blocks, no boxes, no "see also"
   lists. A numbered list only for steps someone will follow in order, and
   a code block only for a command worth copying.
4. End on what to do. One plain sentence pointing to the cleanup checklist
   is enough; no call-to-action box.
5. No em dashes. No Oxford commas. Indian English.
6. Before publishing, read it aloud. Cut any sentence that only says
   something is important, any contrast that knocks down a claim nobody
   made, and any closing line that repeats the paragraph before it.

How it credits sources, like a journalist:

7. Name the source once, where its information appears, with the link on
   its name: "OpenSourceMalware found that ...", "SafeDep traced ...". Do
   not put a citation after every sentence.
8. Keep each source's qualifiers ("about", "reports", "at this time") and
   say only the link a source states. Attribution is a claim like any
   other: MicrosoftSystem64 was once described on this site as PolinRider's
   own implant, and no source said so.
9. No numbers, dates, names or file paths that are not in a source you have
   read. If something cannot be confirmed, leave it out or say plainly that
   it is unconfirmed.
10. End with a short Sources list: publisher, title as a link, date. Our own
    indicator review goes there too.
11. At most two or three links to our own pages in the whole article, placed
    where they help. Link them from the site root, for example
    [the cleanup checklist](/docs/guides/getting-rid-of-polinrider/), never
    with the site's address: the build fails if a page names it
    (scripts/check-base.mjs).

Safety:

12. Never invent or extend an indicator. Name only indicators already in
    ioc/ and recorded in a review. Never print a payload, a full key or
    anything a reader could paste into a working attack. Never quote a line
    of ioc/strong.txt or a match for ioc/strong-patterns.txt: a .mdx page is
    not exempt from the repository's own self-scan, which fails CI on a
    confirmed indicator.
13. Re-check every claim against its source before publishing.

The post links the review it came from through `review` in the front
matter. Nothing links back from the review: reviews are never edited after
they merge.
