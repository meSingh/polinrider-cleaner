polinrider gives one of three answers. `COMPROMISED` means it found something
only the malware leaves. A `[review]` line means nothing is confirmed, but a
person has to decide. Clean means none of today's indicators is present, which
is not proof that nothing was ever there. Here is what each one means and what
to do next.

## The three answers

<div class="verdicts">
<Verdict kind="compromised" code={2} title="Compromised">
You see `VERDICT: COMPROMISED` and `[HIT]` lines. It found at least one
thing that only the malware leaves.
</Verdict>
<Verdict kind="review" code={1} title="Review">
You see `VERDICT: no confirmed indicator.` and `[review]` lines. Nothing is
confirmed, but some lines need a person to decide.
</Verdict>
<Verdict kind="clean" code={0} title="Clean">
You see `VERDICT: clean against the current indicator set.` None of today's
indicators is present. That is not proof that nothing was ever there.
</Verdict>
<Verdict kind="none" code={3} title="Could not run">
A message says the check could not run, for example because a path does not
exist or a GitHub login is missing. It tells you nothing either way.
</Verdict>
</div>

Scripts and CI can rely on these exit codes
([Exit codes](/docs/reference/exit-codes/)).

## How it decides what is confirmed

One rule. An indicator may confirm infection only if a match has no
plausible innocent explanation. Anything a legitimate project could also
contain is review-only. When the two are close, it goes to review.

The reason is part of the rule: a false confirmation costs every user a
panic, while keeping a real indicator at review costs one line of output
([Indicator reviews](/news/indicator-reviews/)).

So take a `[HIT]` at its word, and read a `[review]`.

## If you see COMPROMISED

The box under the verdict says one of two things
([ADR-0034][adr-0034]):

- **"This machine cannot be trusted until it is rebuilt."** Something proves
  the payload ran on this computer: the implant, a login item, a git hook, an
  editor extension, a startup file, a process or a live connection.
- **"The payload is in your project files. See below."** Everything found is
  inside your projects. The payload runs when an infected project is built or
  opened in an editor. If that happened, or you are not sure, treat the
  computer as compromised and rebuild it.

Below the box, **WHAT TO DO NEXT** lists a step for each thing found, with
the exact command. Follow it in order. Check this computer before you touch
GitHub ([Order matters](/docs/guides/order/)). The whole sequence, with what
the tool does at each step, is in
[Getting rid of PolinRider: a developer's guide](/docs/guides/getting-rid-of-polinrider/).

## If you see review lines

The tool prints three steps. In its own words
(from [`src/scan.rs`][scan-rs]):

1. "Read each [review] line. It names a file, a process or a setting. Ask
   whether you put it there."
2. "A [review] line that says a check could not run, or was skipped, means
   that part was not looked at."
3. "If one of them is not yours, treat it as confirmed: disconnect from the
   network, and rotate your credentials from a different machine."

The second step matters. A review line can mean "I could not look", not "I
found something". Fix what stopped the check and run it again.

## Matches that are usually harmless

Each of these is review-only, or not reported at all, because a normal
project can have it. Each still deserves one question: did you or your team
put it there?

### A `tasks.json` that runs on folder open

The line says to verify the command by hand. Teams use folder-open tasks for
real work.

**It is real if** the command runs `node` on a font file, or downloads and
runs something. With a known indicator in it, it is a `[HIT]`, not a review
([`src/checks.rs`][checks-rs]).

### `folderOpen` or `allowAutomaticTasks` in another file

For example in `.vscode/settings.json`. Only `tasks.json` runs commands, so
the words alone do nothing elsewhere
([False positives](/docs/reference/false-positives/);
[`ioc/weak.txt`][weak]).

**It is real if** a `tasks.json` uses them.

### A long build config

A tail after `export default`, or a line longer than 4,000 characters. Some
configs legitimately run long, and a flat ESLint config opens with
`export default [`
([False positives](/docs/reference/false-positives/)).

**It is real if** code you did not write sits after the end of the config,
often after a long run of spaces.

### `public/fonts/fa-solid-900.woff2`

It is a genuine Font Awesome file name ([OpenSourceMalware][osm-ab]).

**It is real if** its first bytes are not a font's. A fake font is a `[HIT]`
whatever it is called
([A font file that is really JavaScript](/news/2026-11-04-fake-font-javascript/)).

### `spellright.dict`, `branch_structure.json` or `clr_init.vbs`

A real VS Code extension's dictionary, or names a legitimate tool could also
write ([ADR-0048][adr-0048]).

**It is real if** nobody on the team uses the tool that writes it, or it sits
beside other campaign files.

### `temp_auto_push.bat` named in a committed `.gitignore`

The repository itself may hold no payload.

**It means** a contributor's computer is infected
([Found temp_auto_push.bat in your repository?](/news/2026-11-04-temp-auto-push-bat/)).

### Never reported

A Git LFS pointer standing in for a font, and an empty font file. Neither has
font bytes, and neither is malware
([False positives](/docs/reference/false-positives/)).

## If you see clean

None of the current indicators is on what was checked. The campaign changes
its signatures, so an older or rotated variant could have been there and gone
([Exit codes](/docs/reference/exit-codes/)).

The tool says so itself: if you had a reason to check, rotate your
credentials anyway. They may have been taken from another computer or a
shared secret store ([`src/scan.rs`][scan-rs]).

Check that it looked where you meant: this computer, the folder that holds
your projects and, if you push code, your GitHub account or organization.

## If your antivirus flagged it

A detection named for PolinRider, such as Windows Defender's
`Trojan:NPM/PolinRider.SF`, is not a false alarm to wave away. In the case in
[PolinRider keeps coming back after you clean it](/news/2026-11-04-polinrider-keeps-coming-back/),
Defender caught the payload's command line as it ran.

A clean result from another scanner is a first pass, not a clean bill of
health. OpenSourceMalware says this of its own scanner, which was built
against the campaign's original signature
([A Developer's Guide to Getting Rid of PolinRider][osm-guide]).

## Found a wrong answer?

Both directions are worth reporting.

- A harmless file reported as `[HIT]`, or a review line that should never
  fire:
  [open a false-positive issue](https://github.com/meSingh/polinrider-scanner/issues/new?template=false-positive.md).
- Something real that was missed:
  [open a missed-detection issue](https://github.com/meSingh/polinrider-scanner/issues/new?template=missed-detection.md),
  with the source you saw it in.

:::tip[Check yours]
Download `polinrider` from the [quick start](/docs/quick-start/)
and run it with no arguments. It asks what to check (this computer, a GitHub
account or an organization) and changes nothing until you type `yes`.
:::
