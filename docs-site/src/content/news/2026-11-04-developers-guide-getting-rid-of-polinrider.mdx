In August, [OpenSourceMalware][osm-guide] published a cleanup guide for
developers infected with PolinRider, drawing on a write-up by developers who
had been through it. Most of it still holds. The campaign has kept changing,
though, and a few of the guide's steps now miss things. If you are cleaning up
a computer or a GitHub account this week, this is what we would add. It comes
from cleaning up one account of our own: 57 repositories and 304 branches and
tags.

## The order still matters most

Nobody is logging in to your account from somewhere else. A script on your own computer uses the
Git credentials already stored there, amends your last commit with the
payload, sets the clock back so the date still matches and force-pushes. Then
it waits for its next trigger and does it again. Changing your password while
that computer is infected only hands it the new one.

So the computer comes first. We would move one step, though. The guide changes
credentials after cleaning GitHub. We do it before, because a token left on an
infected machine is what pushes the payload back into a repository you have
just cleaned, and that can happen within minutes.

Tell your collaborators on day one. In September OpenSourceMalware described
an organization where three separate cleanups were each undone by a
force-push from a different contributor's account, the fastest about five
hours later, under a commit message the team already trusted. Your clean
repository stays clean only while every laptop that pushes to it is clean.

## What has moved on the computer

The guide tells you to search for one fake font file. Since then the same
researchers have watched the name change to other weights and to a `.llf`
extension that is not a font at all, sometimes buried several folders deep.
Check the first four bytes instead. A real web font starts with `wOF2` or
`wOFF`, and the fakes do not.

The payload has also stopped sticking to a fixed list of config files. It
reads the project for a file that actually runs and injects there. And one
loader is written entirely in escape codes, so a plain text search finds
nothing. SafeDep traced that loader to 35 infected repositories in September,
and by our count 18 of them carried the escaped version.

Two kinds of persistence are worth checking by hand. The first is the guide's own find: npm's `cli.js`
replaced with a copy of about a megabyte, so every `npm` command starts the
payload again, even after a reboot. If you find it, uninstall Node.js, make
sure nothing is still running and reinstall. The second is newer.
Deception.Pro watched an operator on a decoy network plant a scheduled task, a
Run key and a Startup script, all named `MicrosoftCLROptimization` after a
real .NET component. A developer on the BleepingComputer forums later posted
logs with the same name in their own Run key, after Defender kept removing the
payload and it kept coming back. We wrote that case up in
[PolinRider keeps coming back after you clean it](/news/2026-11-04-polinrider-keeps-coming-back/).
Look through your Run values and scheduled tasks for that name yourself.

## Whether to wipe the machine

The guide says a factory reset is not needed if you follow its steps in order,
because the payload does not stay on disk between runs. That was a fair
reading in August. The replaced `cli.js` and the logon entries are both files
that stay, so we use a simpler rule. If anything is set to start the malware
again, such as a login item, a startup entry, a git hook or an editor
extension, rebuild the machine. If everything you found sits inside project
files and you know nothing infected was built or opened, clean up and keep
scanning. If you are not sure, rebuild.

## Getting GitHub back

The guide suggests cleaning each file in GitHub's web editor, so you never
pull infected code down again. That works for one file on one branch. It
leaves the infected commit in the history and never touches tags. You still
have to find every repository yourself, including the ones you have not
opened in months.

Going back to an earlier commit is better where you can, but the dates are
forged, so you cannot pick one by date. GitHub's own record of each push
cannot be forged. It shows every force-push with the account that made it,
GitHub's own time and the commit the branch pointed at before. But the commit
before an attack is often the previous attack. On our account, two of ten restore points we found were already infected. Check each one
before you go back to it, and do it soon: GitHub only serves that old commit
until it clears out unreferenced data.

Expect familiar names in that record. The malware pushes as whoever is logged
in, so a colleague's name there means their computer needs checking too.

## What stays with you

Changing credentials, deciding whether to rebuild, removing startup entries
and telling the people you work with are all yours. Use the guide's
credential list: some victims never saw a strange GitHub login, because what
was taken was a Vercel or Netlify token with its own push access. Our
[cleanup checklist](/docs/guides/getting-rid-of-polinrider/) puts every step on one page, with what the scanner does and what it leaves to you.
