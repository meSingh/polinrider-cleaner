## Upstream state

The dossier has not moved in fourteen weeks. No primary analysis of a new
PolinRider wave was published between 2026-10-12 and 2026-10-19 that this
review could find. What was published:

- **OpenSourceMalware, "GhostAction Copycats PolinRider by Hiding a Stealer in
  a Fake Font File", 2026-10-16.** A cluster of 94 repositories, 79 analysed,
  received a second stage that is PolinRider's launcher with a different
  payload. The `.vscode/tasks.json` is a hidden `eslint-check` task with
  `runOn: folderOpen` that runs `node ./public/fonts/fa-solid-400.woff2`, and
  the "font" is 38 lines of plain JavaScript. It steals credential files and
  SSH keys, posts them to `193.32.204.199:8080`, and installs a cron entry
  tagged `#ghc2` that fetches and runs a script every five minutes. The source
  is explicit: "There's no shared IOCs between GhostAction and any other DPRK
  malware we've seen, so at this time we're labeling this a copycat rather than
  an extension of PolinRider." See considered and not added, and the note on
  the existing `strong.txt` entry below.
- The same post found one repository, `daxitzadafiya/bagisto-dhs`, carrying
  both GhostAction and a genuine PolinRider infection: three Tailwind configs
  with the TRON/Aptos/BSC loader appended after ~1,700 spaces, force-pushed on
  2026-06-25 with `temp_auto_push.bat` added to `.gitignore`. The source says
  its "blockchain addresses, keys and delimiter match the PolinRider indicators
  we already track". Nothing new to add from it.
- **OpenSourceMalware, "How to Investigate a GitHub Repo's Real History",

### The OpenSSF search, keyed on last week's C2

`95.216.232.162`, the `MicrosoftSystem64` C2 that week added to `network.txt`,
and `launchkeeper`. Of the 83 records it returned, 81 were already in
`bad-packages.txt`, in its hijacked-versions comments, or among the eight

last week's search could not have found them:

- **`pino-ulid`** (MAL-2026-16154, published 2026-09-14). The same postinstall
  dropper as `ulid-xyz`: the same 8-byte XOR key, the same C2 on port 8010, the
  same `deploy_binary` command and the same `os.cpus()` sandbox check. But the
  agent is renamed: its persistence is
  `~/Library/LaunchAgents/com.launchkeeper.pkg-agent.plist`,
  `~/.config/systemd/user/pkg-agent.service`,
  `~/.config/autostart/pkg-agent.desktop` and a Run value and task named
  `pkg-agent`. Fully unpublished on npm.
- **`redis-type-xyz`** (MAL-2026-11205, published 2026-06-17). An empty copy
  of Redis OM whose only effect is to depend on `ulid-xyz`. **It is still live
  on npm** (latest `2.1.1`, which depends on `ulid-xyz ^3.2.0`). All three
  versions were published by one throwaway account, `qmtijao982`, within two
  hours, and the name belongs to no legitimate package. The maintainer may want
  to report it to npm.

## Considered and not added

**`sass-format` in `weak.txt`.** Weighed first, because it is also a
conceivable task or script label, and a `tasks.json` is matched as content, so a
task labelled `sass-format` would read as a confirmed hit. Rejected because
`weak.txt` is a substring match: `ci/scan-workspace.sh` put a review line on a
fixture whose only content was a manifest naming `sass-formatter`, which has
about 750,000 downloads a week. That is certain noise against a speculative
false positive, and it is the noise whole-name matching was built to remove.
The residual risk is recorded here for the maintainer to overrule.

**`~/.config/systemd/user/pkg-agent.service`,
`~/.config/autostart/pkg-agent.desktop`, and the `pkg-agent` Run value and
scheduled task.** From the same `pino-ulid` record. `pkg-agent` is a name a
legitimate tool could use, and `implant-paths.txt` is INFECTED tier with no
weaker path tier. The LaunchAgent is carried because of its `com.launchkeeper`
prefix; these two have nothing equivalent. The Run value and task are host
state, not an indicator line.

**`pkg-agent` in `implant-names.txt`.** The agent runs as `node payload.js`,
not as a binary called `pkg-agent`, and the name is generic. See techniques.

**The `pino-ulid` payload hash, `3a9089e9…0a7c6a50`.** `dist/node/payload.js`,
about 456 KB. `hashes.txt` only fires on files between 10 MB and 300 MB or on an
`implant-paths.txt` path, so it would never be compared: the small-file hash gap,
carried below.

**Everything from GhostAction**: `193.32.204.199`, the `#ghc2` crontab marker,
the `eslint-check` task label, the `DEVBOX` report header, the seven
second-stage workflow names, the four file hashes and the `Ov23ctrqCqZ79UaYKwyq`
OAuth client ID. The source labels it a copycat with no shared indicators.
`ioc/` is PolinRider's set, and `network.txt` is described to users as campaign
infrastructure and an egress block list. Whether this tool should also carry a
copycat that borrows the launcher is a maintainer decision; see notes.

**`nestjsx/nest-access-control` and `daxitzadafiya/bagisto-dhs`.** Victim
repositories, not indicators.

**The July 2026 Socket package list.** `thehackernews.com` is reachable again,
so its July article on the 108 packages was read in full. It gives counts by
ecosystem (19 npm, 10 Composer, 61 Go, one Chrome extension) and no names. The
list is still only on socket.dev.

**The other 81 OpenSSF records.** Already in `ioc/` or in its comments.

## New techniques — maintainer decisions, not implemented

1. **The `MicrosoftSystem64` agent is being renamed.** `pino-ulid` installs the
   same agent as `ulid-xyz`, with the same key and C2, as `pkg-agent`. Every
   per-OS path in `implant-paths.txt` and every name in `implant-names.txt` is
   keyed on `MicrosoftSystem64`, so the only thing that catches this build on a
   machine is the one LaunchAgent added today, on macOS. A check keyed on the
   `com.launchkeeper.` prefix in `~/Library/LaunchAgents`, rather than on full
   file names, would survive the next rename. On Linux and Windows nothing
   catches it yet. This reinforces item 2 of 2026-10-12: a check for a running
   `node` whose script sits under a known agent directory.
2. **A crontab check.** The GhostAction copycat persists as a crontab line
   that pipes a fetched script into `bash`, tagged `#ghc2`. Nothing here reads
   the user's crontab. If the maintainer decides copycats are in scope, a check
   that flags a crontab line piping `curl` or `wget` into a shell would catch
   this and the next copycat with a different tag.
