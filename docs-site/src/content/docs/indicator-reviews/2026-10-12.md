### Why the OpenSSF search found ten more names this week

The 2026-10-05 search keyed on the Ethereum dead-drop indicators: the `0xa322`
wallet in both cases, `/0x/cls` and the `33ff3eda…` sender check. It found 71
records. This week the key was widened to every indicator in `ioc/` that a
record's prose could quote — `MicrosoftSystem64`, the four TRON wallets, the
campaign UUID, `x-payload-b64`, `test26330331` and the literal word
`PolinRider`. That returned 62 records. **None was published after
2026-10-04**, so this is not new campaign activity: it is ten names from April
to July that the previous search shape could not reach.

- Two records describe themselves in their own words as "part of PolinRider
  campaign": `tailwindthml-flips` and `tailwind-typography-cssstyle`, April
  2026, Amazon Inspector and indece.
- Eight install the `MicrosoftSystem64` second stage: the same three per-OS
  directories `implant-paths.txt` carries, the same
  `com.launchkeeper.MicrosoftSystem64.plist` LaunchAgent, the same systemd and
  autostart names, and — for the three `toskypi` / `nhpkevte1576` packages —
  the same C2, `195.201.194.107:8010`, already in `network.txt`. Five pose as
  the `ulid` library.

All ten were checked against `registry.npmjs.org` on 2026-10-12. Every one is
the `0.0.1-security` placeholder, which is what npm leaves when it treats a
package as wholly malicious rather than hijacked, so the name alone is a
finding. For the substring trap: a registry search on each name, plus direct
lookups of the obvious superstrings (`neo-terminal`, `geo-terminal`,
`video-terminal`, `eo-terminals`, `hex-types`, `hex-typed`, `color-hex-type`,
`is-hex-type`, `msc-terminals`, `logger-drafts`, `check-ulids`, `index-ulids`,
`void-ulids`, `@types/hex-type` and others), found nothing published that
contains any of them.

## Considered and not added

**`bink@DESKTOP-N8JGD6T`.** The comment on the attacker RSA key that the
`eo-terminal` payload appends to `~/.ssh/authorized_keys` (MAL-2026-4345). A
match would mean infection with no plausible alternative, so it is
`strong.txt`-grade — but nothing would ever compare it. `strong.txt` is matched
by the local check only inside build configs, `tasks.json`, hooks, extensions
and manifests, never in `~/.ssh`; the precedent is the one that keeps
small-file hashes out of `hashes.txt`. See techniques: this wants a check, not a
line.

**`yszf984308/system-release`.** The Hugging Face repository the `toskypi`
packages exfiltrate to. The same record says the configuration strings are XOR
and base64 obfuscated in `dist/config.js`, so the name does not occur in a
scanned file. Unlike `Lordplay/system-releases` and `jpeek998/system-releases`,
which `strong.txt` carries as delivery locations, no source here says this one
appears in plain text.

**The XOR key `[90, 60, 126, 18, 159, 75, 109, 138]`.** Readable as an array
literal in the source's description, but whether the file writes it with spaces,
without, or minified is not stated, and a fixed string has to bet on one.

**The HKCU Run key, the scheduled task name `\MicrosoftSystem64`,
`MicrosoftSystem64.service` and `MicrosoftSystem64.desktop`.** All either
already in `implant-paths.txt` or registry and task-scheduler state, which is a
host check, not an indicator line.

**`~/.pcl-data/offline-queue.jsonl`.** Inside `~/.pcl-data`, already carried.

**The `npm-cache[.]com`, `pypi-get[.]com`, `js-mirror[.]com` domains and the
`0xE1f2395e…` contract.** ChainDrop, per Unit 42 via search summaries. A
separate actor by every account seen, and not readable here regardless.

**Everything in GBHackers and Socket's updated tracker count.** Search summaries

**The other 52 of this week's 62 OpenSSF records.** Already in

**New: `weak.txt` has no effect on the local check.** Found while proving this
week's additions. `polinrider check --fs-only` on a folder whose
`tailwind.config.js` contains `api.trongrid.io`, `files.catbox.moe` and
`hex-type` exits 0 with no review line. In `src/` the weak list is read by the
GitHub path (`remote.rs`) and by nothing else, and `ci/scan-workspace.sh` reads
it too. This is not a 2.0 regression: in 1.x, `lib/local-common.sh` defined
`has_weak` and never called it. But `ioc/README.md` and the docs site both say
the effect of `weak.txt` is a `review` line, and for the machine and folder
checks that has never been true. Whether the folder check should read it is a
maintainer decision; until then, review-tier indicators reach only the CI
scanner and the GitHub checks.

## New techniques — maintainer decisions, not implemented

1. **An `authorized_keys` check.** The `MicrosoftSystem64` RAT in the `toskypi`
   packages appends its own RSA key to `~/.ssh/authorized_keys`, so a machine
   cleaned of the implant can still be entered over SSH. Nothing here reads that
   file for content; the credential inventory lists `~/.ssh` for rotation. A
   check that flags an `authorized_keys` line whose comment matches a list —
   starting with `bink@DESKTOP-N8JGD6T` — would be small, and the cleanup
   advice should say to review `authorized_keys` regardless, since the next
   build can use a different comment.
2. **The JavaScript form of the implant runs as `node`.** The ULID-cluster
   packages copy `payload.js` into the `MicrosoftSystem64` directory and run it
   as `node payload.js --agent`, not as a native binary. `implant-names.txt` is
   matched against the process name only, by design, so this process is
   invisible to the process check; it is caught by the `implant-paths.txt`
   directories and, from this week, by the `.vbs` launcher on Windows. A check
   that asks whether any running `node` has a script under a `MicrosoftSystem64`
   directory would close it without matching a full command line.
3. **Sandbox evasion by core count.** Every record in the family exits when
   `os.cpus().length <= 4`. That means a CI runner or a small VM used to test a
   suspicious package will see nothing, which is worth one sentence in the
   documentation for anyone triaging by running the package.
