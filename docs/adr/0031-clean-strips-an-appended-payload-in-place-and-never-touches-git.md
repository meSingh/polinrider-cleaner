# 0031. clean strips an appended payload in place, and never touches git

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-03 |

## Context

When the machine check finds a build config carrying an indicator it says:
do not edit this file, delete the clone and re-clone after the remote is clean.

That advice is correct and often useless. The payload is appended to a real
file, `postcss.config.mjs` or `next.config.js`, so the file cannot be moved to
quarantine without taking the project's own config with it. And a developer
mid-incident usually has work in that clone that is not pushed anywhere.
"Delete the clone" means "lose it". People do not delete the clone. They open
the file, scroll right for 280 columns, and cut by hand.

Mandeep asked for this early on and the design was agreed on 2026-09-16: strip
the appended payload after the module end, quarantine a copy first, show the
lines in a dry run, never touch git state, and say plainly that history may
still carry the infected commit. This record is that design, built.

Two rules stood in the way, and both are the kind that are not negotiable:
nothing is deleted ever, and `--apply` moves files, it does not edit them.

## Decision

A new command, `polinrider clean REPO...`. It does not change what
`check --apply` means. `check --apply` still moves confirmed artifacts into
quarantine and never rewrites the contents of a file, and a conformance case
pins that.

**`clean` is `check` pointed at working trees, plus one thing.** It runs every
check that reads the directories it was given and none that read anything
else: no home directory, no host state, and it refuses `--home`, `--fs-only`
and `--host-state` instead of ignoring them. The one difference is that an
infected build config is stripped, not just reported.

**Dry run by default.** Without `--apply` it prints the last line it would
keep and the start of what it would cut, and changes nothing.

**The original is kept before anything is changed.** With `--apply`, the file
as found is copied into quarantine and read back. Only then is the cleaned
file written beside the original and renamed over it. If any step fails the
working tree is as it was. The manifest records the copy with the reason
`stripped-config`. Nothing is deleted: the bytes that were cut are in
quarantine, inside the original.

**It cuts one shape and refuses the rest.** The campaign appends the payload
after the real `export default` or `module.exports`, behind a run of padding.
`src/strip.rs` plans a cut only when all of this holds:

- the first indicator in the file is behind a run of at least 64 spaces or tabs
- something that starts a module, `export default` or `module.exports`, comes
  before the cut
- nothing after the cut looks like the project's own code: no `import`, no
  module line, no line that is only a closing bracket
- what would remain has balanced brackets

Otherwise the file is reported with the reason it was not stripped and the old
advice, and it is not touched, `--apply` or not.

**It never touches git, and never runs it.** Nothing is pulled, reset,
stashed, staged or committed, and `.git` is not read. Whether the payload was
committed or only sitting in the working tree makes no difference to the cut.
The output says, every time something is stripped, that the commit which
carried the payload may still be in the repository's history and on its
remote.

**The dry-run guarantee stays a type.** The write lives on
`Quarantine<Apply>::strip`. `Quarantine<DryRun>` has no such method, and a
`compile_fail` doctest proves it on every build, the same as for `take`.

**The exit code reports what was found.** A run that strips a payload exits 2:
a confirmed indicator was there. Running it again exits 0.

## Consequences

Better: the common case, one appended payload in a clone with unpushed work,
goes from "lose your work or cut by hand" to one command that can be undone.

Worse, and worth stating plainly:

- **This tool now edits source.** Every earlier version could say that
  `--apply` only moves files. That sentence is still true of `check` and no
  longer true of the tool. It is on the README and in the documentation and
  has to be reworded, not left to mislead.
- **A cleaned working tree is not a clean repository.** If the payload was
  committed, `git status` shows the strip as a modification and the infected
  commit is still in history, in the reflog and on the remote. A developer who
  sees exit 0 on the second run may stop there. The output says so; that is
  not the same as preventing it.
- **The cut is by shape, not by understanding.** There is no JavaScript
  parser. The bracket check counts brackets inside strings and regular
  expressions too, so it refuses some files it could have handled. That is the
  direction chosen to be wrong in. The other direction is still possible: a
  file with a 64-column run of spaces of its own, followed by an indicator and
  no further code, would be cut at the run. No real config has been seen like
  that; one could exist.
- **A variant that pads less, or not at all, is not stripped.** It is still
  found and reported, so nothing is missed, but the command does nothing for
  it, and the indicator set can be updated weekly while this rule cannot.
- **Not consulting git is a choice with a price.** Comparing the result with
  the committed blob would prove the cut restored the file exactly. It would
  also mean running git inside a repository an attacker has written to, where
  the repository's own config decides what git executes. The proof was given
  up for that. The dry run and `git diff` are how the operator checks instead.
- **Restoring from quarantine re-infects.** For a stripped file the copy in
  quarantine is the infected original. `RESTORE.txt` says so, and somebody
  will run the loop without reading it.
- **Only build configs.** A payload in `tasks.json`, a fake font or a hook is
  still moved whole, as before. A payload appended to any other kind of file
  is outside what the machine check looks at, and so outside this.
